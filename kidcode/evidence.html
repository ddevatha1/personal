KidCode: Three Years of Teaching Python

1,214 Programs Later: What Three Years of Student Code Revealed

September 2026KidCodeDeeptanshu Devatha

I have a folder with every numbered project KidCode students have turned in over three years: 1,214 Python files from 124 students, across the 20 projects in the curriculum. For a long time I treated it as an archive. This fall I treated it as data. I ran every program, counted what was actually in them, and checked the counts against my own tally, project by project. This post is what that showed, what my students' test scores showed, and what none of it shows.

The point isn't to make KidCode sound bigger. It's to write down what can actually be checked.

Every one of the 1,214 programs runs, but it took two passes to show that. The first time through, I fed every program the same generic answers, and 62 of them crashed. None of those crashes was a student bug. A number-guessing game that calls int() on your answer doesn't cope with being told "dragon", and a cipher program that counts letters doesn't cope with being handed "3". Once the answers matched the questions (numbers for number prompts, real sentences for message prompts), all 62 ran to the end. The test says a program works. It doesn't say the program is good, and I'm not claiming it does.

The 1,214 break down into 138 programs from the six Year 1 projects, 504 from the seven in Year 2, and 572 from the seven in Year 3. When I compared the per-project counts with the tally I'd been keeping, all twenty matched.

Year 1 programs are short, with a median of 31 lines. Every one of them uses an f-string. Loops show up in about 72% and conditionals in 79%. Functions show up in only 13%, and every one of those is in the last project, Escape the Haunted School.

Year 2 is where the code changes character. Every Year 2 program defines functions. Nearly half define a class, and every Monster Battle Arena program uses inheritance. Three quarters read or write files, half wrap risky code in try/except, and about half carry their own assert tests. The median Year 2 program is 96 lines, three times the Year 1 median.

Year 3: every program uses spaCy. About a third work with named entities, and just under a quarter write their own rule-based patterns with spaCy's Matcher. The single most-completed project in the whole program is from Year 3: KidBot Brain, a small intent-matching chatbot, with 118 submissions.

The number that surprised me is length. The median Year 3 program is 51 lines, shorter than Year 2. In Year 2, students wrote the text-cleaning and word-counting code themselves. In Year 3, spaCy does that work in one line, and the students' code goes into deciding what to do with the result. Lines of code turned out to be a bad measure of growth.

Two things I taught in Year 3 appear in no student program at all: displaCy, spaCy's visualizer, and entity_ruler, spaCy's way of adding your own entity types. Both are in the curriculum. Neither shows up in the code.

What the tests show

Code tells me what students built. It doesn't tell me what they learned, so each unit also had a curriculum-aligned pre- and post-assessment. The two forms test the same skills in the same formats with different code. I only analyze students who have both scores, so the comparison is the same students before and after. That's 104 students across the three years.

104 students showed a mean increase from 41.7% to 58.8%, a 17.1-percentage-point gain. In relative terms that's a 41% increase over where they started, but I think the points gain is the more honest way to say it. The gain was similar for each starting cohort, between about 15 and 19 points. How individual changes were spread out:

There's no comparison group here: no set of kids who didn't take KidCode and took the same tests. So this shows students scored higher at the end of a unit than at the start. It doesn't show that KidCode is why. I also don't have the individual unit-by-unit scores, only each student's pre and post percentage, so the result can't be broken down by unit.

What these numbers don't show

A program in the folder means a student built it. It doesn't tell me which classes they came to, or whether any of it sticks a year later. I have some attendance totals and some records of who came back the next year, but I'm not publishing numbers from them. The attendance figures are totals without class-by-class records behind them. The return records cover only some of the students, and not a random some. I'd rather leave those out than publish a number I can't defend.

How to check this

The counts and test results in this post, the definitions behind them, and a script that recomputes each one from the published tables are in the KidCode public proof package. No student's name or code is in it. Each project in the class archive shows one real program alongside the numbers for that project.
